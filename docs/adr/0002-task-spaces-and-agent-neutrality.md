# ADR 0002 任务空间、连接隔离与 Agent 中立

日期：2026-11-16。状态：用户已接受，M1 已按此实现。本记录修订 ADR 0001 之后各设计文档中的四项假设。

## 背景

用户明确了产品形态：像 ego 浏览器那样，Codex、Claude Code、DeepSeek 等不同 Agent 都通过 Skill 调用同一个 SSH 工具；Agent 在部署时，用户可以照常使用自己的终端，两边互不影响。

设计基线 0.1 与此有四处差距：只面向 Codex；控制权挂在单个通道上，没有“一个目标一块工作区”的概念；要求同一身份复用同一条连接；Agent 闭环排在第三个里程碑，且常驻服务到那时才出现。

## 决定

### 1. 任务空间是隔离与控制权的单位

Agent 为每个目标打开一个任务空间。空间绑定一台主机，拥有自己的任务、终端和控制权。用户自己的终端是用户创建的空间，Agent 不可见、不可写，也不能被交给 Agent。

控制权从“每个通道”上移到“每个空间”，有三个动作：

- 接管：用户取得 Agent 空间。确认之后，该空间内 Agent 的输入、新任务、上传、中断和关闭全部被拒绝。
- 归还：用户把空间还给 Agent，生成新租约。旧租约永久失效，Agent 必须重新读取空间状态。
- 交接：Agent 主动把空间交给用户并说明原因（例如 sudo 密码、二次验证），用户处理后归还。

接管不终止进程，不关闭连接。读取输出不需要控制权。

### 2. 每个空间一条连接

空间内的任务复用该空间的连接；不同空间不共用连接。原 NFR-002“相同连接身份复用已认证连接”收窄为“同一空间内复用”。

原因：OpenSSH 默认每条连接最多 10 个会话；Agent 的大量输出与用户按键共用一条 TCP 会互相拖慢；一条连接断开不应影响另一方。代价是每个空间多一次握手，对以分钟计的部署任务可以接受。

隔离不到的部分：服务器本身是共享的。两边同时改同一个文件或重启同一个服务，结果取决于先后顺序。工具保证用户能看到 Agent 正在做什么，不承诺阻止这种冲突。

### 3. Agent 中立与引导式 Skill

协议和文档不再假设调用方是 Codex。打开空间时 Agent 报告一个名称，只用于界面显示，不参与授权。

安装到 Agent 目录的 `SKILL.md` 只包含一条指示：先运行 `vibe-ssh skill`。使用说明由 CLI 按已安装版本输出，因此 Skill 不会描述不存在的命令。原决定中安装是用户的显式动作（现由 [ADR 0003](0003-desktop-files-and-onboarding.md) 修订为应用启动自动同步），链接到 `~/.agents/skills` 与 `~/.claude/skills`，已存在且不属于本工具的同名条目保持原样。

任何能执行本机命令行的 Agent 都可以使用；不为某个模型供应商内置适配。

### 4. 常驻服务前移，人工操作不上套接字

桌面应用就是常驻服务，内核运行在应用进程内。Agent 通过当前用户专属的 Unix 套接字访问（目录 0700，套接字 0600，并校验对端用户）。

套接字协议里只有 Agent 能做的事。添加主机、信任指纹、开启 Agent 接入、接管与归还只存在于应用进程内部的调用，协议中没有对应的方法，因此调用方无法通过声明自己是用户来获得人工权限。

里程碑相应调整：

| 阶段 | 原计划 | 现计划 |
| --- | --- | --- |
| M1 | 人工 SSH 客户端 | Agent 闭环：服务、套接字、任务空间、CLI、引导式 Skill |
| M2 | 文件与项目 | macOS 桌面应用：主机管理、凭据、终端、观看与接管 |
| M3 | Codex 控制闭环 | 文件与项目同步的完整策略 |
| M4 | 部署与首版发布 | 不变 |

首版桌面目标收窄为 macOS，Windows 推后。

### 5. 不做内核批处理

原 FR-008 的有序批处理不再实现。每次 `run` 都单独经过租约校验，Agent 逐步调用即可得到“失败即停、接管后不再继续”。需要原子执行的多行步骤通过标准输入作为一个脚本提交；脚本在远端作为一个任务运行，接管只能阻止下一次调用，不能阻止已在运行的脚本的后续行，用户可以中断它。

## 接口兼容性

协议版本由 1 升为 2，不兼容。M0 的 `probe` 与 `capabilities` 命令、每通道 `InputLease` 类型被移除，没有迁移路径：版本 1 只存在于开发验证阶段，从未发布。版本不匹配的请求返回 `VERSION_MISMATCH`。

文件上传使用 SSH exec 通道上的 tar 流，要求远端有 `tar`。本机的打包在调用方进程内完成，归档经套接字流式交给服务：这样服务不会以自己的权限替 Agent 读取本地文件。在 macOS 上应用可能持有 Agent 进程没有的文件访问授权，由服务读取会让 Agent 借此读到本不能读的目录。SFTP 依赖随之移除；需要逐文件语义（浏览、冲突检测）时在 M3 重新引入。

## 比较过的做法

| 做法 | 结论 |
| --- | --- |
| 保持每通道控制权，界面按通道接管 | 接管一个终端后 Agent 仍可另开通道继续执行，不符合“接管后排队步骤不再执行” |
| 所有空间共用一条连接 | 省一次握手，但有会话上限、互相拖慢和同时断开的问题 |
| 人工操作也走套接字，靠令牌区分 | 令牌文件同一用户可读，Agent 进程同样能读到，区分不成立 |
| 独立守护进程，应用只是客户端 | 多一个进程生命周期要管理；当前单用户桌面场景下没有收益，需要无界面运行时再拆 |

## 后果

应用退出后空间和任务随之结束，Agent 收到 `SERVICE_UNAVAILABLE`；远端进程是否仍在运行需要重新查证。任务与输出目前只在内存中，按空间保留最近 64 个任务、每路输出 1 MiB。跨重启的持久记录属于后续工作。
